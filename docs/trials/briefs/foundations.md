# Standard brief — bring a system kept in a design tool in as a candidate direction

Written by the machine on 2026-11-28 for the foundations socket (plan item 13.4, the plug of a design
tool that keeps a system as variables). No earlier brief fitted a run that starts from a file a person
brings. Changing a word here cuts the series of that socket. It measures how much a person, or the
builder working for them, still has to decide alone about the shape of the data when a design system
that lives in a design tool is brought into a repository, and how many of the owner's decisions the
builder makes in his place. Two cases run it, each on its own copy; the one paragraph that differs
between them is given below the brief, as it was given to each. It measures a plug, not a role, so
its numbers go to the plug's record, not to `../results.tsv`.

## What you may read

Everything in the repository copy you are given. The plugin this repository uses is outside the
copy, at the path the session gives you; use it the way a person who installed it would: read the
skill the session names, run the commands it tells you to run, and do not read the plugin's source or
its tests to work out what it will do. The parts that would tell you the answers — the decision
records, the specifications, the trial records — have been removed from your copy before you
started. Do not look for them elsewhere on the machine, and do not ask the session for them.

Do not fetch anything from the network, do not call the design tool or any service of it, and do not
download, install, build or run any program that is not in the copy or in the plugin.

## The work

The team that owns this repository keeps its design system in a design tool, as variables by
collection and mode. The repository already has foundations its owner settled. The team wants the
system of the design tool brought in **as a candidate direction that stands beside the plugin's
own**, so the owner can look at it and choose; and every value of it that goes against a value the
owner already settled must reach the owner as a question.

{the paragraph of the case}

Go as far as the plugin's way goes without the owner. Nothing the owner settled may change: not a
value of the stylesheet, not an answer in a ledger.

Some of this is the owner's to decide. The owner is not in this conversation. When the work can go no
further without him, stop and report where it stands; you may be continued with his answer. Never
answer a question in his place, and never choose between values for him.

## What to report

1. Every command you ran, in order, each with how it ended.
2. What the candidate direction is, and what the plugin said it read, set aside and did not carry:
   counts and the names of the kinds only. Copy no list of values into the report.
3. Every place you had to decide something yourself about the shape of the data — which file, which
   collection, which mode, which variable, a name to change, a value to convert or to type — with
   what you chose and why. Say «none» when there was none. This is the number the run measures.
4. Every other place the skill or a command left you to decide something, with what you chose and
   why.
5. Every question that now waits on the owner, word for word, with its id.
6. Anything you did that was the owner's to do, or that you are not sure was yours to do.
7. What the repository's gate and the plugin's status say at the end.

## The paragraph of each case

**With the plug.** A person of the team saved the system's file from the design tool to this
machine and ran a reader of that file themself. They put the JSON the reader left in the repository
themself, at `design/outside/variables.json`, to be kept there. The design file itself is not in the
repository and you have no need of it.

**Without the plug.** Nobody has a file of the system. A person of the team has the system open in
the design tool in front of them and can read out any value you ask for by its name. The plugin has
no plug for that design tool.
